# Readable Java — 자바 코드 가독성 규칙

이 스킬은 자바 코드를 짤 때 따라야 할 **가독성의 기본 규칙**을 정의한다.
Java 코드를 쓰는 모든 순간에 적용된다.

구체적인 Before/After 예시는 같은 디렉토리의 `reference.md`를 참고할 것.
규칙이 추상적으로 느껴지면 즉시 `reference.md`의 해당 섹션을 열어보고 비교한다.

도메인 객체 설계, Tell Don't Ask, VO, 일급 컬렉션, 다형성 같은 객체지향 설계 규칙은
별도 스킬 `oop-java`로 분리되어 있으므로 이 문서에서는 다루지 않는다.
테스트 코드 작성 규칙도 별도 스킬로 분리되어 있다.

---

## 0. 핵심 원칙

코드를 짤 때 머릿속에 항상 두는 두 가지 질문이다.

1. **이 코드를 처음 읽는 사람이 한 번에 이해할 수 있는가?**
2. **이 한 줄의 의도가 코드 자체로 드러나는가, 아니면 추측해야 하는가?**

둘 중 하나라도 "아니오"이면 다시 손본다.

### 0-1. 적용 강도는 작업 규모에 비례한다

가독성 규칙은 항상 적용되지만, **얼마나 깊게 들어갈지는 작업 규모에 맞춘다.**
한 줄 고치는데 메서드 추출까지 들이대지 않는다.

- **한두 줄 추가/수정** → 이름, null 처리, 명백한 안티패턴 회피 정도
- **새 메서드/클래스 작성** → 추상화 레벨, early return, 메서드 길이까지
- **명시적 리팩토링 요청** → 메서드 추출, 구조 정돈까지

## 1. 이름 짓기 (Naming)

### 1.1 변수명: 의미를 드러낸다
- `i`, `j`, `c`, `r`, `input`, `input2`, `temp`, `data` 같은 이름 금지.
- 이중 for문 인덱스는 `row`, `col`로 쓴다. `i`, `j`는 의미를 잃는다.
- 입력값은 무엇을 입력받았는지로 명명: `cellInput`, `userActionInput`.
- boolean은 `is`, `has`, `can`, `does`로 시작: `isOpened`, `hasLandMineCount`, `canUseLocker`.

### 1.2 메서드명: 동작과 의도를 명확히
- 부정형 단어를 이름에 박지 말고, 긍정형 메서드를 만들고 호출 측에서 부정한다.
  - 나쁨: `isNotEmpty()` 호출 → `if (!isNotEmpty())` 가독성 최악.
  - 좋음: `isEmpty()` 정의 → `if (!isEmpty())`.
  - 단, 의미상 부정형이 자연스러운 경우(`cannotUseLocker()` 같이 비즈니스 개념 자체가 부정형)는 허용.
- 메서드명은 한 가지 동작만 가리키도록: `getCellPositionFromUser()`, `findPassCandidatesBy(passType)`.

### 1.3 상수: 매직 넘버/매직 스트링 추방
- 코드에 등장하는 모든 리터럴 숫자/문자열은 **이름이 있어야** 한다.
- `8`, `10`, `"□"`, `"☼"` 같은 값을 그대로 박지 말고 `BOARD_ROW_SIZE`, `LAND_MINE_SIGN` 등 상수로.
- 예외: `0`, `1`, 명백히 자명한 인덱스(`array[0]`) 같은 케이스만.

### 1.4 클래스명: 책임을 드러낸다
- `Manager`, `Helper`, `Util` 같은 모호한 접미사는 책임이 불분명하다는 신호다. 더 구체적인 이름을 찾는다.
- 클래스가 표현하는 개념이 명확하면 그 이름을 그대로 쓴다: `CellPosition`, `GameBoard`.

## 2. 메서드 작성 규칙

### 2.1 추상화 레벨을 맞춘다 (가장 중요)
하나의 메서드 안에서는 비슷한 추상화 수준의 코드만 모인다.
- 나쁨: 고수준 흐름과 저수준 디테일이 한 메서드에 섞여 있음.
- 좋음: 고수준 메서드는 고수준 메서드만 호출하고, 디테일은 더 깊은 메서드로 내려간다.

판단 기준: 메서드 본문을 읽었을 때 "무엇을 하는지"가 한 줄 한 줄 같은 높이의 설명이어야 한다.

### 2.2 Early Return으로 들여쓰기 줄이기
- if-else 체인 대신 조건 불만족 시 즉시 return / throw.
- guard clause로 예외 케이스를 먼저 걸러내고, 정상 흐름은 들여쓰기 없이 작성.

### 2.3 사고의 depth 줄이기
- 중첩 for문, 중첩 if문은 2단계까지를 한계로. 그 이상은 메서드 추출.
- 컬렉션 순회는 가능하면 stream으로 의도를 드러낸다 (`noneMatch`, `anyMatch`, `filter().toList()`).
- 단, stream이 오히려 가독성을 해치면 for문이 낫다. 무조건 stream이 정답은 아님.

### 2.4 메서드 선언부 정리
- 파라미터 개수가 3개를 넘으면 객체로 묶을 수 있는지 의심한다.
- boolean 파라미터는 분기 의도를 드러내지 못한다. 가능하면 메서드를 둘로 나누거나 enum으로.
- 반환 타입은 `null`보다 `Optional`을 우선 고려.

### 2.5 메서드 길이
- 한 메서드는 한 화면(20~30줄) 안에 들어오도록.
- 길어지면 일단 추출 가능한 블록이 없는지 본다. 보통 주석이 달린 블록이 추출 후보다.

### 2.6 클래스 내 멤버 선언 순서
클래스 내부의 멤버는 다음 순서로 나열한다:
1. 상수(static final)
2. 인스턴스 필드
3. 생성자
4. 정적 팩토리 메서드 (`of`, `from`)
5. public 메서드 (외부에 노출되는 행위)
6. private 메서드 (내부 헬퍼)
7. getter

호출하는 메서드를 위에, 호출되는 메서드를 아래에 두면 위에서 아래로 읽힌다.
getter를 맨 아래에 두면 비즈니스 행위가 먼저 눈에 들어와 객체의 역할이 강조된다.

## 3. 제어 흐름과 가독성

### 3.1 해피 케이스와 예외 처리
- 정상 흐름(happy path)이 코드의 주류가 되도록 배치한다.
- 예외/실패 케이스는 먼저 걸러내고 정상 흐름을 평면적으로 작성.
- 예외는 무시하지 말고 의미 있는 메시지로 던진다.
- `catch (Exception e)` 하나로 다 잡지 말고, 구체적인 예외부터 잡고 마지막에 unknown fallback.

### 3.2 공백 라인의 역할
- 공백 라인은 "여기서 사고의 단락이 바뀜"을 알리는 신호다.
- 메서드 내부에서 의미 단위가 바뀌는 곳에 한 줄 띄운다.
- 무조건 띄우거나 무조건 붙이는 게 아니라, 문단을 나누는 감각으로.

### 3.3 부정어 다루기
- 이중 부정은 피한다 (`!isNotEmpty()` 금지).
- 조건문에 부정형이 너무 많으면 긍정 메서드로 뽑아낸다.

## 4. 작성 체크리스트

코드를 다 짠 후 마지막으로 점검한다.

- [ ] 메서드 이름만 보고 무엇을 하는지 알 수 있는가
- [ ] 변수명에 `i`, `j`, `temp`, `data` 같은 무의미한 이름이 없는가
- [ ] 매직 넘버/스트링이 남아있지 않은가
- [ ] 추상화 레벨이 한 메서드 안에서 섞이지 않았는가
- [ ] depth가 3 이상으로 깊어진 곳이 없는가
- [ ] if-else 체인을 early return으로 풀 수 있는 곳이 없는가
- [ ] boolean 파라미터로 분기 의도를 숨긴 메서드가 없는가
- [ ] null을 반환하는 메서드가 있다면 Optional로 바꿀 수 없는가
- [ ] 클래스 내 멤버가 [상수 → 필드 → 생성자 → 정적 팩토리 → public → private → getter] 순인가
- [ ] 이중 부정(`!isNotXxx()`)이 남아있지 않은가

> 도메인 객체 설계, 책임 분리, Tell Don't Ask 같은 항목은 `oop-java` 스킬에서 점검한다.

## 5. reference.md 사용법

각 규칙의 구체적인 Before → After 코드는 `reference.md`에 정리되어 있다.
규칙을 적용할지 헷갈리거나, 어떻게 고칠지 막막할 때는 다음 순서로 본다:

1. SKILL.md에서 해당 규칙 번호를 확인 (예: `2.1 추상화 레벨 맞추기`)
2. reference.md에서 같은 번호 섹션을 찾는다
3. Before 코드의 어떤 부분이 문제였고, After에서 어떻게 풀었는지 비교

각 예시는 자체 완결적이라 실제 도메인을 모르더라도 패턴만 이해하면 적용할 수 있도록 작성되어 있다.
